# دليل منصة ريستا على Google Cloud

هذا الدليل يشرح كيف تركّب منصة ريستا على Google Cloud، وكيف تربطها بـ Cloudflare وGitHub وموقع resta.sa، وكيف تتحكم في السيرفرات والمطاعم والفوترة من شاشة واحدة داخل أودو.

---

## 1. الصورة العامة

```
                 ┌──────────────────────────── Cloudflare ───────────────────────────┐
  صاحب المطعم ──▶│  kaffa.restaerp.com   beno.restaerp.com   control.restaerp.com     │
                 └───────────┬───────────────────┬───────────────────┬───────────────┘
                             │ 443               │ 443               │ 443
                 ┌───────────▼───────────┐ ┌─────▼───────────────┐ ┌─▼────────────────────────┐
                 │ خلية مشتركة cell-01   │ │ سيرفر خاص (كاستم)  │ │ سيرفر المنصة             │
                 │ أودو 19 + PostgreSQL  │ │ main + staging      │ │ أودو 19 + resta_platform │
                 │ حتى 10 علامات         │ │ لعميل واحد          │ │ (الفوترة والتحكم)        │
                 │ الوكيل :8090 ◀────────┼─┼── الشبكة الداخلية ──┼─┤                          │
                 └───────────┬───────────┘ └─────────┬───────────┘ └─────────┬────────────────┘
                             │ نسخ احتياطي ليلي مشفّر  │                       │ Compute API
                             ▼                       ▼                       ▼
                  محلي + Google Cloud Storage + تخزين مزوّد ثالث      يفتح ويغلق السيرفرات
```

ثلاثة أجزاء فقط:

| الجزء | وين يشتغل | وش يسوي |
|---|---|---|
| **المنصة** (`resta_platform`) | سيرفر واحد صغير | تسجيل العملاء، الباقات، الفواتير، فتح السيرفرات من Google، أوامر الإيقاف والتشغيل والنسخ، مراقبة الأداء |
| **الوكيل** (`agent`) | على كل سيرفر مطاعم | ينفّذ أوامر المنصة: ينشئ قاعدة مطعم، يوقفها، ينسخها، يسترجعها، يحدّث الكود، ويرسل النتيجة للمنصة |
| **سكربت التجهيز** (`bootstrap_cell.sh`) | يشتغل مرة وحدة عند ولادة السيرفر | يركّب Docker والوكيل ويسجّل السيرفر في المنصة تلقائياً |

**قاعدة مهمة:** المنصة هي المرجع الوحيد. أي تغيير (مطعم جديد، إيقاف، نسخة) يبدأ منها وينفّذه الوكيل. لا أحد يدخل السيرفرات يدوياً إلا للطوارئ.

### محتوى المستودع

```
restash/
├── odoo/                        أودو 19 Community المخفف
├── resta_addons/                موديولات ريستا + نسختا الصالة والوجبات السريعة
```

كل السيرفرات تبني **صورة ريستا** من `Dockerfile` المستودع، وتشغّل النسختين على **Community فقط** (`resta_account` و`resta_payroll` و`resta_barcode` بدل Enterprise).

## 2. التجهيز في Google Cloud (مرة واحدة)

### قبل كل شيء: الفوترة عن طريق CNTXT

الشركات اللي عنوان فوترتها في السعودية **لازم تشتري Google Cloud عن طريق CNTXT** (الموزع الحصري)، لأي منطقة، ومنطقة الدمام `me-central2` ما تفتح إلا لعملاء CNTXT ([المصدر](https://docs.cloud.google.com/docs/dammam-region-access)). لذلك ربط بطاقة مباشرة في Google يعطي خطأ «تم رفض الوصول… تحقق من حساب الفواتير».

1. ادخل [cloud.cntxt.com](https://cloud.cntxt.com) واضغط **Continue with Google** بنفس حساب Google اللي فيه المشروع (للشركات: إيميل Google Workspace).
2. أكمل تسجيل الشركة، والدفع بالبطاقة (Visa أو Mastercard أو مدى).
3. بعد تفعيل حساب الفوترة: في Google Cloud ← **الفوترة** ← اربط المشروع بحساب CNTXT.

### أسهل طريقة: سكربت واحد

بعد ما تصير الفوترة فعّالة، افتح **Cloud Shell** (الزر `>_` أعلى لوحة Google Cloud) والصق محتوى الملف [`infra/gcp/setup_google.sh`](../infra/gcp/setup_google.sh) كاملاً. يسوي كل خطوات هذا القسم (2.1 إلى 2.5) ويطبع في النهاية القيم اللي تحتاجها لاحقاً. الخطوات تحت للتوضيح أو للتنفيذ اليدوي. غيّر `resta-prod` لرقم مشروعكم.

### 2.1 المشروع والخدمات

```bash
gcloud config set project resta-prod
gcloud services enable compute.googleapis.com storage.googleapis.com iap.googleapis.com
```

- اربط المشروع بحساب فوترة.
- من **IAM & Admin → Quotas** تأكد أن منطقة **me-central2 (الدمام)** فيها حصة كافية: `CPUS` (24 على الأقل) و`STATIC_ADDRESSES` (10 على الأقل). اطلب الزيادة مبكراً لأنها تأخذ يوم أو يومين.

### 2.2 الجدار الناري

السيرفرات تُعرف بوسمين: `resta-platform` لسيرفر المنصة و`resta-cell` لسيرفرات المطاعم (المنصة تضع الوسم تلقائياً).

```bash
# 1) الإنترنت يدخل فقط عن طريق Cloudflare على 443
gcloud compute firewall-rules create resta-https-cloudflare \
  --network=default --direction=INGRESS --action=ALLOW --rules=tcp:443 \
  --source-ranges="$(curl -s https://www.cloudflare.com/ips-v4 | paste -sd,)" \
  --target-tags=resta-cell,resta-platform

# 2) المنصة فقط تكلّم الوكيل على 8090
gcloud compute firewall-rules create resta-agent-from-platform \
  --network=default --direction=INGRESS --action=ALLOW --rules=tcp:8090 \
  --source-tags=resta-platform --target-tags=resta-cell

# 3) سيرفرات المطاعم تسجّل وترسل النتائج للمنصة على 8069 (داخلي)
gcloud compute firewall-rules create resta-cells-to-platform \
  --network=default --direction=INGRESS --action=ALLOW --rules=tcp:8069 \
  --source-tags=resta-cell --target-tags=resta-platform

# 4) الدخول للطوارئ عبر IAP فقط (بدون فتح SSH للإنترنت)
gcloud compute firewall-rules create resta-ssh-iap \
  --network=default --direction=INGRESS --action=ALLOW --rules=tcp:22 \
  --source-ranges=35.235.240.0/20 --target-tags=resta-cell,resta-platform
```

إذا كانت شبكة `default` فيها قاعدة `default-allow-ssh` مفتوحة للعالم، احذفها:
`gcloud compute firewall-rules delete default-allow-ssh`

> **ملاحظة:** نطاقات Cloudflare تتغير نادراً. حدّث القاعدة الأولى كل ستة أشهر بنفس الأمر مع `update` بدل `create`.

### 2.3 حسابات الخدمة (الصلاحيات)

نحتاج حسابين، كل واحد بأقل صلاحية ممكنة:

```bash
PROJECT=resta-prod

# حساب المنصة: يفتح ويغلق السيرفرات فقط
gcloud iam service-accounts create resta-platform --display-name="Resta Platform"
gcloud projects add-iam-policy-binding $PROJECT \
  --member="serviceAccount:resta-platform@$PROJECT.iam.gserviceaccount.com" --role=roles/compute.instanceAdmin.v1
gcloud projects add-iam-policy-binding $PROJECT \
  --member="serviceAccount:resta-platform@$PROJECT.iam.gserviceaccount.com" --role=roles/compute.publicIpAdmin

# حساب سيرفرات المطاعم: يكتب النسخ الاحتياطية فقط
gcloud iam service-accounts create resta-cell --display-name="Resta Cells"
gcloud iam service-accounts add-iam-policy-binding resta-cell@$PROJECT.iam.gserviceaccount.com \
  --member="serviceAccount:resta-platform@$PROJECT.iam.gserviceaccount.com" --role=roles/iam.serviceAccountUser

```

لا نحتاج مفتاح JSON: سيرفر المنصة يشتغل بحساب `resta-platform` نفسه (الخطوة 2.5)، فالمنصة تأخذ صلاحياتها منه مباشرة. هذا أسلم، ويتجاوز سياسة المؤسسات الجديدة اللي تمنع إنشاء المفاتيح.

### 2.4 مخزن النسخ الاحتياطية

```bash
gcloud storage buckets create gs://resta-prod-backups --location=me-central2 --uniform-bucket-level-access
gcloud storage buckets add-iam-policy-binding gs://resta-prod-backups \
  --member="serviceAccount:resta-cell@resta-prod.iam.gserviceaccount.com" --role=roles/storage.objectAdmin
gcloud storage buckets add-iam-policy-binding gs://resta-prod-backups \
  --member="serviceAccount:resta-cell@resta-prod.iam.gserviceaccount.com" --role=roles/storage.legacyBucketReader
```

### 2.5 سيرفر المنصة

```bash
gcloud compute addresses create resta-platform-ip --region=me-central2
gcloud compute instances create resta-platform \
  --zone=me-central2-a --machine-type=e2-standard-2 \
  --image-family=ubuntu-2404-lts-amd64 --image-project=ubuntu-os-cloud \
  --boot-disk-size=60GB --boot-disk-type=pd-balanced \
  --address=resta-platform-ip --tags=resta-platform \
  --service-account=resta-platform@resta-prod.iam.gserviceaccount.com --scopes=cloud-platform
```

### 2.6 الإيميل الصادر

Google Cloud **يقفل المنفذ 25** لكل السيرفرات. لإرسال إيميلات الترحيب والفواتير استخدم خدمة إرسال (مثل Zoho Mail أو Amazon SES أو Brevo) على المنفذ **587**، وأدخلها في المنصة من: الإعدادات العامة ← الخوادم الصادرة.

## 3. Cloudflare

1. أضف النطاق `restaerp.com` إلى Cloudflare وغيّر الـ Nameservers عند المسجّل.
2. **SSL/TLS ← Overview**: اختر **Full (strict)**.
3. **SSL/TLS ← Origin Server ← Create Certificate**: للنطاقين `restaerp.com` و`*.restaerp.com` لمدة 15 سنة. احفظ:
   - الشهادة ← تُستخدم في سيرفر المنصة وفي إعدادات المنصة (حقل «شهادة Origin»).
   - المفتاح الخاص ← نفس الشيء (حقل «مفتاح شهادة Origin»). **يظهر مرة وحدة فقط.**
4. **My Profile ← API Tokens ← Create Token ← Edit zone DNS**: الصلاحية `Zone.DNS: Edit` على `restaerp.com` فقط. انسخ المفتاح.
5. من صفحة النطاق الرئيسية انسخ **Zone ID**.
6. أضف سجل `A` باسم `control` يشير إلى عنوان سيرفر المنصة الخارجي، والسحابة البرتقالية **مفعّلة**.

سجلات المطاعم (`kaffa.restaerp.com` وغيرها) **تنشئها المنصة تلقائياً** عند تجهيز كل مطعم.

## 4. GitHub

أنشئ مفتاح **Fine-grained token** من: Settings ← Developer settings ← Personal access tokens.

- **Repository access:** المستودعات المطلوبة فقط (`restash` ومستودع نسخة ريستا، و`enterprise` إذا عندكم وصول).
- **Permissions:** `Contents: Read-only` فقط. لا تعطه صلاحية كتابة أبداً.
- مدة الصلاحية: سنة، وضع تذكير بتجديده.

## 5. تركيب المنصة

```bash
# الدخول للسيرفر عبر IAP
gcloud compute ssh resta-platform --zone=me-central2-a --tunnel-through-iap

# على السيرفر:
sudo mkdir -p /opt/resta-platform/certs
sudo nano /opt/resta-platform/certs/origin.pem   # الصق شهادة Cloudflare
sudo nano /opt/resta-platform/certs/origin.key   # الصق المفتاح الخاص
curl -fsSL -H "Authorization: token <GITHUB_TOKEN>" \
  https://raw.githubusercontent.com/walsoodi/restash/staging/infra/platform/install_platform.sh -o install.sh
sudo GIT_TOKEN=<GITHUB_TOKEN> bash install.sh
```

السكربت:
- يركّب Docker، يسحب الكود، يبني صورة ريستا (أول مرة 10–15 دقيقة)، وينشئ كلمات سر عشوائية لقاعدة البيانات وأودو (محفوظة في `/opt/resta-platform/.env`).
- ينشئ قاعدة `platform` ويركّب موديول **منصة ريستا** باللغة العربية.
- يشغّل أودو خلف nginx بشهادة Cloudflare.
- في آخره يطبع **رابط المنصة الداخلي** (مثل `http://10.208.0.2:8069`) — انسخه.

بعدها افتح `https://control.restaerp.com`، ادخل بـ `admin / admin`، **وغيّر كلمة السر فوراً** وفعّل التحقق بخطوتين.

## 7. أول سيرفر مطاعم (خلية)

1. **منصة ريستا ← السيرفرات ← جديد**.
2. النوع: **خلية مشتركة (ساس)**، المزوّد: **Google Cloud**. الاسم مثل `cell-01`.
3. اضغط **إنشاء في Google Cloud**.

وش يصير خلف الكواليس (حوالي 20–25 دقيقة لأول مرة: بناء صورة ريستا ثم القالبين):

```
المنصة                        Google Cloud                      السيرفر الجديد
  │ يحجز عنوان IP ثابت ─────────▶│                                   │
  │ ينشئ السيرفر + سكربت التجهيز ▶│── يشغّل السيرفر ────────────────▶│
  │                               │                                   │ يركّب Docker والوكيل
  │◀──────────── طلب تسجيل (مفتاح صالح لمرة وحدة) ───────────────────│
  │ يرسل الإعدادات: كلمات السر، أماكن النسخ، الشهادة ───────────────▶│
  │                                                                   │ يشغّل PostgreSQL وأودو وnginx
  │ يفحص الصحة ──────────────────────────────────────────────────────▶│
  │ «جاهز» ثم يبني القوالب (صالة / وجبات سريعة) ─────────────────────▶│
```

تتابع الحالة في السيرفر: `مسودة ← قيد الإنشاء ← جاهز` (أو `ممتلئ` لاحقاً، و`لا يستجيب` إذا انقطع). تبويب **الأداء** يعرض المعالج والذاكرة والقرص وعدد القواعد كل 5 دقائق.

## 8. أول مطعم

### يدوياً من المنصة

1. **منصة ريستا ← المشاريع ← جديد**.
2. النوع **ساس**، اختر الباقة والعميل، اكتب **الكود** (يصير الرابط: `kaffa.restaerp.com`)، إيميل مدير النظام، عدد الفروع.
3. اضغط **إنشاء النظام**.

المنصة تختار أقل خلية امتلاءً، تنشئ سجل الـ DNS، وتطلب من الوكيل نسخ القاعدة من القالب (ثوانٍ بدل دقائق)، ثم تضبط اسم الشركة واللغة العربية وكلمة سر مؤقتة، وترسل **إيميل الترحيب** فيه الرابط وبيانات الدخول.

### تلقائياً من موقع resta.sa

مطوّر الموقع يرسل:

```bash
curl -X POST https://control.restaerp.com/resta/api/signup \
  -H "Content-Type: application/json" \
  -H "X-Resta-Key: <مفتاح التسجيل>" \
  -d '{
        "brand_name": "كفة",
        "code": "kaffa",
        "email": "owner@kaffa.sa",
        "contact_name": "محمد",
        "phone": "+9665xxxxxxxx",
        "edition": "dinein",
        "branches": 2
      }'
```

الرد (`201`):

```json
{"project_id": 12, "code": "kaffa", "url": "https://kaffa.restaerp.com", "state": "provisioning", "trial_end": "2026-12-02"}
```

ثم يتابع الحالة كل 10 ثوانٍ حتى تصير `active` (الحالات: `queued` بانتظار سيرفر، `provisioning` قيد الإنشاء، `active` جاهز، `error` خطأ يراجعه فريقكم):

```bash
curl https://control.restaerp.com/resta/api/project/kaffa -H "X-Resta-Key: <مفتاح التسجيل>"
```

| الخطأ | المعنى |
|---|---|
| `401` | مفتاح التسجيل غلط |
| `400` | بيانات ناقصة أو الكود محجوز/مستخدم |

> الأكواد المحجوزة: `www, admin, api, app, mail, control, platform, resta, staging, test` وأي كود يبدأ بـ `tpl`.

## 9. التحكم اليومي

### أزرار المشروع (المطعم)

| الزر | وش يسوي | يتوقف النظام؟ |
|---|---|---|
| **فتح النظام** | يفتح رابط المطعم | لا |
| **نسخة احتياطية الآن** | نسخة مشفّرة في كل أماكن النسخ | لا |
| **إيقاف** | يقفل الدخول ويعرض صفحة «النظام موقوف». البيانات محفوظة | نعم |

### شاشة العمليات

كل أمر يصير **عملية** لها رقم (`OP-000123`) وحالة: `بانتظار ← قيد التنفيذ ← تمت / فشلت`. إذا فشلت عملية تشوف السبب في السجل، والمنصة تعيد المحاولة تلقائياً حتى 6 مرات بفواصل متزايدة (خلال ساعتين تقريباً). تقدر تضغط **إعادة المحاولة** أو **إلغاء**.

## 10. الفوترة

- كل مشروع مربوط بباقة: **الأساس + (الفروع الإضافية × سعر الفرع) + التخزين الإضافي**.
- كل مشروع له **تاريخ الفاتورة القادمة**: أول فاتورة بعد نهاية التجربة، ثم كل شهر. المنصة تصدرها تلقائياً كل يوم للمشاريع المستحقة.
- إذا تأخر السداد أكثر من **مهلة السداد**: يُوقف النظام تلقائياً (سبب الإيقاف: عدم السداد).
- بمجرد تسجيل الدفعة على الفاتورة في المحاسبة: **يرجع النظام يشتغل تلقائياً**.
- الإيقاف اليدوي لا يرجع تلقائياً مع السداد.

## 11. التوسع التلقائي

كل 5 دقائق المنصة تقرأ أداء كل خلية. الخلية تُعتبر **ممتلئة** إذا وصلت لعدد العلامات المحدد (10) أو تجاوز حملها **حد الامتلاء** (70%)، والحمل هو أعلى قيمة بين المعالج والذاكرة والقرص.

إذا امتلأت كل الخلايا وكان **التوسع التلقائي** مفعّلاً، تفتح المنصة خلية جديدة بنفس طريقة القسم 7، والمطاعم الجديدة تروح لها تلقائياً. المطعم الجديد **ما يُرفض أبداً**: إذا ما فيه مكان، يدخل حالة **«بانتظار سيرفر»**، والمنصة تجهزه تلقائياً أول ما تصير خلية جاهزة (تجربته المجانية تبدأ من لحظة التجهيز الفعلي). وإذا التوسع التلقائي غير مفعّل، يوصل للمدير تنبيه «كل الخلايا ممتلئة — افتح خلية جديدة».

## 12. النسخ الاحتياطي والاسترجاع

- كل ليلة **02:30 بتوقيت الرياض** نسخة لكل قاعدة مع ملفاتها، مشفّرة، في **ثلاثة أماكن**: السيرفر نفسه، Google Cloud Storage، والمزوّد الثالث.
- الاحتفاظ: **7 يومية + 4 أسبوعية + 3 شهرية**.
- قبل كل **تحديث إنتاج** تؤخذ نسخة تلقائياً.

### الاسترجاع (للمدير)

1. من المشروع اضغط **تحديث قائمة النسخ** (ثوانٍ).
2. اضغط **استرجاع نسخة**، تظهر قائمة النسخ بأرقامها وأوقاتها.
3. اكتب رقم النسخة، أو اتركها `latest` لآخر نسخة.
4. اختر الطريقة:

| الطريقة | وش يصير | متى تستخدمها |
|---|---|---|
| **كنسخة تجربة للفحص** | تُفتح على `kaffa-staging.restaerp.com` محيّدة، والإنتاج ما يتأثر | دائماً أولاً: للتأكد أن النسخة هي المطلوبة، أو لاستخراج بيانات انحذفت بالغلط |
| **استبدال قاعدة الإنتاج** | تكتب كود المشروع للتأكيد، النسخة تحل مكان الإنتاج، والقاعدة الحالية **لا تُحذف** بل تُحفظ باسم جانبي | عند كارثة فعلية (بيانات تلفت) |

الوكيل يرفض أي رقم نسخة لا يخص نفس المطعم، فما يمكن استرجاع بيانات مطعم على مطعم ثاني بالغلط.

## 13. المشاريع الخاصة (كاستم)

1. أنشئ سيرفر بنوع **سيرفر خاص (كاستم)** واختر حجمه حسب العميل.
2. أنشئ مشروع بنوع **كاستم**، وفي تبويب **الكود (كاستم)** حدد مستودع العميل وفرع الإنتاج وفرع التجربة.
3. السيرفر الخاص فيه بيئتين منفصلتين: `main` للإنتاج و`staging` للتجربة، كل وحدة بكودها.
4. سير العمل: المطوّر يرفع على فرع التجربة ← **تحديث التجربة** ← العميل يختبر ← بعد موافقتكم **تحديث الإنتاج**.

## 14. الأمان

- كل أمر من المنصة للوكيل **موقّع** بمفتاح سري خاص بكل سيرفر (HMAC-SHA256) ومعه وقت؛ أي طلب بدون توقيع صحيح أو أقدم من 5 دقائق يُرفض.
- الوكيل يسمع على **العنوان الداخلي فقط**، والجدار الناري يسمح للمنصة وحدها.
- التسجيل يتم بمفتاح يُستخدم **مرة وحدة**.
- المطاعم ما تشوف قائمة القواعد، وكل مطعم ما يفتح إلا قاعدته (حسب اسم الرابط).
- الإنترنت يدخل فقط عبر Cloudflare، وSSH فقط عبر IAP.
- النسخ مشفّرة، ومفتاح GitHub قراءة فقط.
- الأسرار (كلمات السر والمفاتيح) محفوظة في المنصة وتظهر للمدير فقط.

## 15. للمطوّرين: عقد الوكيل

| المسار | الطريقة | الوصف |
|---|---|---|
| `/v1/health` | GET | المعالج والذاكرة والقرص والقواعد وحجم كل قاعدة والقوالب الجاهزة |
| `/v1/jobs` | POST | أمر جديد: `{"operation_id": "...", "type": "create_db", "params": {...}}` |
| `/v1/jobs/<id>` | GET | حالة أمر |

**التوقيع:** `X-Resta-Timestamp` (ثوانٍ) و`X-Resta-Signature = hex(HMAC_SHA256(secret, timestamp + "." + body))`.

**أنواع الأوامر:** `create_db`, `build_template`, `suspend`, `resume`, `backup`, `restore`, `duplicate`, `drop`, `deploy`, `create_stack`, `snapshots`, `backup_all`.

الوكيل يرجع `202` فوراً، ينفّذ في الخلفية، ثم يرسل النتيجة موقّعة إلى `/resta/agent/callback` في المنصة (ويعيد المحاولة إذا فشل الإرسال). وإذا ضاعت النتيجة، المنصة تسأل الوكيل عن الحالة بنفسها. نفس `operation_id` لا يُنفّذ مرتين.

**الاختبارات:**

```bash
cd agent && python3 -m pytest -q                       # 14 اختبار
odoo-bin -d test_db -i resta_platform --test-tags /resta_platform --stop-after-init   # 18 اختبار
```

تم أيضاً تشغيل تجربة كاملة حقيقية: المنصة ← الوكيل ← بناء قالب ← إنشاء مطعم ← إيقاف ← تشغيل ← نسخة احتياطية في مكانين، وكل النتائج رجعت للمنصة موقّعة.

وعلى مشروع ريستا نفسه (أودو المخفف): النسختان تتثبتان كاملتين بدون أخطاء (168 و179 موديول، دقيقتان لكل قالب)، والمطعم الجديد يُنسخ من القالب في 3 ثوانٍ بالعربي والريال وشجرة الحسابات السعودية.
